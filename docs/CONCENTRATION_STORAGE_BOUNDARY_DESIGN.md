# Concentration storage-failure boundary (repair in progress)

Starting code/docs commit: 59f89e816320706f337491fc07c2e28dbf87c09f. Work happens in a separate proposed-patch worktree. No release sign-off. Existing pending-turn/attack continuations do not yet establish this failure boundary.

A damage HP write commits before the Concentration owner persists its save/decision. If that second write fails, its transaction also rolls back the newly captured continuation. A 500 warning alone does not stop later effects in the same command or leave a durable interruption after restart. Reproduce with a scoped Concentration UPDATE failure during Burning, then assert Command/timers do not proceed and the campaign remains durably blocked.

The intended owner correction is a small execution journal in the existing combat_paused_work table. When a tracked concentrating monster takes damage (or a tracked cast must end due to an already-committed death/Incapacitated condition), record an interrupted/running work item in the SAME transaction as that triggering state change. This joins the existing HP/condition writers through their transaction owner; it never performs a second connection's query inside that transaction. A failed journal insert must roll back the state change. Ordinary success closes the journal only after the full request, including costs/logs, finishes. A pending decision captures the exact continuation into that same work item. A crash or write failure leaves it blocked for review, even when the Concentration-row transaction rolled back.

Recovery must not reroll HP damage or blindly replay an uncertain step. The GM sees the persisted damage facts and available original save outcome, reviews/corrects the state/costs, explicitly settles the tracked cast, then may resume the known remaining steps. A fresh review token must prevent a duplicate recovery request from acknowledging a later interrupted attempt on the same work id. Unknown roll/state remains explicit; no outcome is guessed. Voluntary ending of an active monster cast is grounded in the supplied SRD 5.2.1 p.179 (the creator may end Concentration at any time); it needs cast identity and GM-scoped reads/edits, separate from answering a pending failure.

Required controls: original failing route probe; rollback if journal creation fails; Concentration UPDATE failure after HP commit; death/Incapacitated cleanup failure after the triggering state commit; cold-process recovery of an interruption; stored damage/save facts; no later effect/timer/resource progression; both permitted GM recovery decisions; stale/duplicate review and cast tokens; player/foreign campaign exclusion; request and direct-owner concurrency; no private state in player surfaces. Mutation-check the guarantees, update both handoffs/API docs, then run a clean full race/shuffle suite. This is a design and test plan, not an implementation or validation claim.

## Implementation and evidence, 2026-11-18

The separate `monster-durable-concentration-guard` worktree now joins `journalMonsterConcentrationIn` to the existing fight/HP transaction or condition-owner transaction. This adds `context` and `review_token` columns to the existing `combat_paused_work` table, in the same application database. No new database, external dependency, deployment or upstream mutation.

A healthy command ignores only its own running obligation, completes costs/logs, and closes only its own work id. Pending decisions capture into that work id. Errors/panics leave it interrupted. The shared pause reader also checks the current request's recorded DB failures, preventing the rest of a failed command from running even if its Concentration transaction rolled back. Original complete `game.SaveResult` is saved to the journal before that transaction; it is never rerolled during recovery. If journal creation fails, HP/condition changes roll back with it.

`GET /api/gm/combat-resume` privately exposes event context and the current review token. After reviewing/correcting the uncertain step, the GM submits a note and that token: `reconcile` closes work after manual completion; `reconcile_and_resume` continues only the stored known remainder. A conditional token update excludes duplicate/stale reviews and rotates the token for the next attempt. Resume also rotates it when claiming ready work. Legacy work with no token has a derived one-time review identity. No automatic replay of the uncertain operation.

`GET /api/gm/monster-concentration` privately lists active casts and their identities. `POST` with decision `end_cast` and the observed `cast_token` voluntarily ends that exact cast, including after a write failed before recording a pending decision (SRD 5.2.1 p.179). Alternatively, the GM can use the existing Legendary Resistance command to correct the persisted failed save, retaining the cast, then record that review. The server does not guess which correction the GM selected.

A second independently reproduced defect: `conditionTakesHold` only sent the old untracked-cast reminder for monsters. Stunned therefore did not end a tracked cast until damage occurred. `TestPostgresConcentrationIncapacitatedEndsImmediately` failed before correction (`incapacitated-immediate-before.log`). The shared condition owner now calls the tracked lifecycle owner immediately; untracked effects still receive a private reminder.

Focused results so far (not a complete-suite claim): the original turn/storage probe passes; a failed journal INSERT rolls back HP; death and Incapacitated DELETE failures preserve the committed triggering state and leave a durable boundary; both GM recovery workflows pass; an owner-level two-caller review race accepts one token once; a fresh server process finds and recovers the interrupted command without repeating Burning.
